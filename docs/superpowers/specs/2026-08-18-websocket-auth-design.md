# WebSocket Authentication Hardening Design

Date: 2026-08-18

## Context

The relay currently authenticates WebSocket clients with a shared token in the
connection URL. The web client stores that token in `localStorage` and appends
it as `?token=...` during the WebSocket handshake. Telegram and the TUI also
receive a relay URL that may contain the token. This creates avoidable exposure
through URLs, diagnostics, exception messages, browser tools, and proxy logs.

The public web frontend is deployed from the personal fork to
`https://herdr-remote-bfd.pages.dev`. The relay remains bound to loopback and
will later be exposed through a Cloudflare Tunnel. No tunnel may be started
until this design is implemented, tested, deployed, and configured.

## Goals

- Never put the relay token in a WebSocket URL.
- Authenticate every token-protected WebSocket before sending snapshots or
  accepting commands.
- Keep the browser token in memory only and remove legacy persisted copies.
- Preserve Telegram and TUI operation through one shared protocol.
- Restrict browser connections to configured trusted origins.
- Keep authenticated HTTP relay operations working with Bearer tokens.
- Remove executable third-party JavaScript from the web page.
- Avoid printing, logging, committing, or returning real token values.

## Non-goals

- Replacing the shared secret with user accounts or OAuth.
- Adding Cloudflare Access in this change.
- Rotating the existing token unless verification finds evidence of exposure.
- Redesigning relay commands or agent authorization after authentication.
- Changing the separate `herdr.push` repository in this change.

## Protocol

Protocol version 1 uses a first-message authentication exchange over the
established WebSocket.

Client to relay:

```json
{"type":"auth","protocol":1,"token":"<shared-secret>"}
```

Relay to client after successful validation:

```json
{"type":"auth_result","protocol":1,"ok":true}
```

When `HERDR_RELAY_TOKEN` is configured, the relay must not send an agent
snapshot or process any other message before successful authentication. The
first message must arrive within five seconds, be valid JSON, use protocol 1,
and contain an exact token match checked with a constant-time comparison.

For a missing, malformed, unsupported, or incorrect authentication message,
the relay closes the connection with WebSocket policy code `1008` and the
generic reason `Unauthorized`. It does not echo the token or distinguish the
failure cause.

When no relay token is configured, the existing unauthenticated local behavior
remains available for backward compatibility. No production tunnel setup will
use that mode.

## HTTP authentication

Non-WebSocket HTTP requests continue to use
`Authorization: Bearer <shared-secret>`. Query-token handling remains accepted
temporarily for compatibility but is not generated by any client or installer
in this repository. Removing that compatibility path requires coordination
with external push clients and is outside this change.

Public static asset routes and the VAPID public-key route retain their existing
access rules.

## Origin policy

`HERDR_RELAY_TRUSTED_ORIGINS` is a comma-separated set of exact browser origins.
For this installation it will contain:

```text
https://herdr-remote-bfd.pages.dev
```

During a WebSocket upgrade:

- a browser request with an `Origin` header must match the configured set;
- a mismatched browser origin receives HTTP 403 before the upgrade;
- a non-browser client without an `Origin` header may continue to authenticate
  with the shared token;
- an empty trusted-origin configuration preserves compatibility but logs a
  startup warning when token authentication is enabled.

This policy allows the Pages frontend, Telegram, and the TUI while preventing
another website from initiating an authenticated browser session.

## Client changes

### Web

- Remove the executable import from `esm.sh`; cue calls remain optional no-ops.
- Delete any legacy `herdr_relay_token` value from `localStorage` on startup.
- Hold the submitted token in a module-scoped in-memory variable only.
- Clear the password input immediately after copying its value to memory.
- Open the clean relay URL without a token query.
- Send the versioned `auth` message on `open` and mark the UI live only after a
  successful `auth_result`.
- Clear the in-memory token when changing sessions or selecting the demo.
- Require token entry again after refresh or browser restart.

Saved session records continue to contain only a display name and relay URL.

### Telegram

- Read the token from `HERDR_RELAY_TOKEN` rather than relying on the relay URL.
- Use a shared authentication helper immediately after every connection,
  including short-lived command connections and the persistent listener.
- Strip a legacy `?token=` from `HERDR_RELAY` in memory. If the dedicated token
  variable is absent, migrate the legacy value into memory for that process so
  an existing installation continues to start without transmitting it in the
  URL.
- Keep redaction for Telegram and relay secrets in all errors and logs.

### TUI

- Use the same clean URL and shared authentication helper as Telegram.
- Do not report `connected` until authentication succeeds.
- On authentication failure, disconnect and retry without logging the token.

### Installer

- Store `HERDR_RELAY` as a token-free URL.
- Store `HERDR_RELAY_TOKEN` only in the owner-readable secrets file.
- Preserve file mode `0600` for secrets.
- Add `HERDR_RELAY_TRUSTED_ORIGINS` to non-secret configuration when supplied.

## Implementation boundaries

- `relay/herdr_relay.py` owns server-side origin validation and the
  authentication state gate.
- A small relay client helper owns URL sanitization and the versioned client
  handshake for Python clients.
- `relay/herdr_telegram.py` and `relay/herdr_tui.py` call that helper rather
  than implementing authentication independently.
- `web/security.js` owns pure browser-side connection and migration helpers.
- `web/index.html` owns DOM state and connection lifecycle.
- `relay/install-service.sh` owns persisted environment layout.

No unrelated relay command or UI refactoring is included.

## Error handling

- Authentication timeout, malformed JSON, wrong protocol, and wrong token all
  produce the same external close response.
- Server logs may record that authentication failed, plus remote address and
  origin, but never the submitted token or raw authentication message.
- Browser, Telegram, and TUI errors use sanitized relay URLs.
- A trusted-origin failure returns only `Origin not allowed` and never starts a
  WebSocket session.

## Testing

Tests are written and observed failing before production changes.

Relay tests cover:

- successful authentication before the first snapshot;
- invalid authentication closing without a snapshot;
- timeout, malformed JSON, and unsupported protocol;
- rejection of an untrusted browser origin;
- acceptance of the configured Pages origin;
- unchanged unauthenticated behavior when no token is configured;
- unchanged Bearer authentication for protected HTTP requests.

Client tests cover:

- clean WebSocket URLs with no token query;
- correct versioned authentication messages;
- removal of legacy browser storage;
- migration of legacy Python client URLs without retransmitting the query;
- authentication before Telegram and TUI commands or state handling;
- absence of executable third-party script sources in the web application.

The project test suite, syntax checks, and relevant installer tests must pass
before commit or push.

## Rollout

1. Add failing protocol, client, migration, origin, and asset tests.
2. Implement the relay gate and Python client helper.
3. Migrate web, Telegram, TUI, and installer configuration.
4. Run focused tests and the complete project suite.
5. Commit only related files and push only to `maxto/herdr-remote` on
   `feat/multi-session-local`.
6. Verify the automatic Pages deployment serves the new frontend.
7. Add the exact Pages origin to the local relay configuration and restart the
   user relay service without exposing or rotating the token.
8. Re-run local authenticated checks.
9. Ask for a separate explicit authorization before starting any public tunnel.

## Success criteria

- No maintained client sends a relay token in a URL.
- No web token survives a page refresh.
- An unauthenticated connection receives no agent data and cannot run commands.
- The personal Pages origin authenticates successfully.
- A different browser origin is rejected before WebSocket upgrade.
- Telegram and TUI pass their existing behavioral tests with token auth enabled.
- The full project suite passes and the deployed frontend contains no executable
  third-party script import.
